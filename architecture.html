Architecture

Guidelines

  • Lightweight: one process, SQLite, no build pipeline for the front end.
  • Config as code: YAML and Markdown, git-friendly.
  • Secure by default: permission checks on the server; secrets never in the browser or in content.
  • Open: Apache-2.0, no dependency on external services to operate it.

Building blocks

  • Stack: TypeScript, Hono, rendered on the server (hono/jsx). The browser gets JavaScript only where it is needed (SurveyJS forms).
  • One configuration schema (Zod) for wegaria.yaml. config/wegaria.schema.json for IDE completion is generated from it.
  • Access: a Principal (id, name, e-mail, groups) from forward-auth headers (only from trustedProxies), native OIDC or the dev mode. access: { groups, deny, public } is inherited from top to bottom and always evaluated on the server; anything not visible answers with 404. See Authentication.
  • Status: no checker of its own. Providers for Uptime Kuma, Prometheus and Gatus (plus a generic HTTP/JSONPath provider for widgets) run in the backend, with a stale-while-revalidate cache, timeout, size limit and no redirects. Credentials never leave the server. See Status.
  • Content (content/): category.yaml, *.faq.md, *.form.yaml, _assets/; ids are paths. A broken file keeps its last good version. See Service area.
  • Forms: the SurveyJS runtime (MIT licence; the Creator is commercial and is not used). Input is validated again on the server with survey-core. After that come SQLite (submission, retention period, audit) and a durable queue for the actions email, webhook (signed) and git (backoff, retry, status in the administration). Targets and credentials live in wegaria.yaml, never in content. No script execution.
  • Notices: incidents and maintenance from Markdown files (also editable in the administration) and/or from Uptime Kuma status pages. They colour affected tiles without making a worse measured status look better.
  • Sessions in SQLite (only a hash of the session id), tokens encrypted (session.key). Groups are re-read regularly with the refresh token; back-channel logout ends sessions immediately.
  • Operations: configuration and content are reloaded live; auth, baseUrl and the directories need a restart. See Deployment.

User interface

One design system made of CSS variables: colour means state, one configurable accent, light and dark mode, mobile first, usable without JavaScript. Details and an inventory are in docs/ui/ in the repository. Pages share the header, grid and building blocks (ui.tsx, admin-shell.tsx); accessibility is checked automatically. Customisation is described in Appearance.
