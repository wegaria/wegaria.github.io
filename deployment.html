Deployment

Image

docker build -t wegaria:local .
docker run --rm -p 3000:3000 -v "$PWD/config:/config:ro" -v wegaria-data:/data wegaria:local
  • Base image node:22-bookworm-slim (with git for the git action). It runs as the user node, without root rights.
  • /config (read-only): wegaria.yaml, content/, optional assets/ (logo). Changes are picked up without a restart.
  • /data (volume): the SQLite database with submissions, queue and audit log. Back it up.
  • Environment: WEGARIA_CONFIG (default /config/wegaria.yaml), WEGARIA_DATA (/data), PORT (3000).
  • The HEALTHCHECK queries /healthz (works without sign-in; use it directly on the container, not through Traefik).
  • The image works with read_only: true, cap_drop: [ALL] and no-new-privileges (as in the Compose example).

Compose example: Traefik and Authelia (forward auth)

Files in deploy/: compose.yaml, .env.example, config/ (starting configuration).

  1. Create a network with a fixed subnet in which Traefik and Wegaria sit:
    docker network create --subnet 10.250.0.0/24 proxy
    Traefik must be attached to this network. Enter the subnet in config/wegaria.yaml under auth.trustedProxies. Wegaria trusts the identity headers only from these addresses. If another container sits in the same network, it could forge the headers: only Traefik (and Wegaria) belong in this network, ideally a dedicated one per application.
  2. cp .env.example .env, set WEGARIA_HOST, and adjust baseUrl in config/wegaria.yaml.
  3. docker compose up -d --build

Wegaria publishes no ports. If it is reachable directly, anyone can set the headers themselves, because the trust check knows only the source address.

Authelia middleware

Traefik needs a ForwardAuth middleware called authelia. If it does not exist yet, define it on a container with traefik.enable=true and a service port, for example Authelia itself:

traefik.http.middlewares.authelia.forwardauth.address: http://authelia:9091/api/authz/forward-auth
traefik.http.middlewares.authelia.forwardauth.trustForwardHeader: "true"
traefik.http.middlewares.authelia.forwardauth.authResponseHeaders: Remote-User,Remote-Groups,Remote-Name,Remote-Email

authResponseHeaders must contain all four headers that Wegaria reads (auth.headers in the configuration). Tested with Traefik v3: Traefik then replaces any value sent by the client. If a header is missing from the list (for example Remote-Groups), Traefik passes a client-supplied value through unchanged and a signed-in user could give themselves arbitrary groups. For that reason compose.yaml additionally removes the four headers before authentication (wegaria-strip-identity). This is a second safeguard against exactly this configuration error. Middleware order: first wegaria-strip-identity, then authelia.

Status page without login (optional)

If /status should be reachable without login (for example when the login itself is down), you need a second router without the Authelia middleware that takes precedence. Wegaria shows non-signed-in visitors only content with access: { public: true }. The state of an otherwise invisible internal service can be released with status: { ..., public: true } (Docker: wegaria.status.public), without detail text. See Status. With native OIDC, auth.public: true is enough; only the forward-auth setup needs a proxy router.

traefik.http.routers.wegaria-status.rule: Host(`${WEGARIA_HOST}`) && Path(`/status`)
traefik.http.routers.wegaria-status.priority: "100"
traefik.http.routers.wegaria-status.entrypoints: websecure
traefik.http.routers.wegaria-status.tls: "true"
traefik.http.routers.wegaria-status.middlewares: wegaria-strip-identity   # keep removing the identity headers
traefik.http.routers.wegaria-status.service: wegaria

Feedback widget on the same host (optional)

With feedback: { key: pk_..., identify: true } in wegaria.yaml (see Feedback), Wegaria inserts a script tag /_feedback/widget.js. It does not serve the widget itself: Traefik forwards exactly two paths on the same host to the feedback service. This keeps the CSP (script-src 'self', connect-src 'self') unchanged, and the feedback service sees the real client address. The labels sit on the Wegaria container; the service feedback@docker comes from the Compose file of the feedback service (its Traefik Compose file):

traefik.http.routers.wegaria-feedback.rule: Host(`${WEGARIA_HOST}`) && (PathPrefix(`/_feedback/v1`) || Path(`/_feedback/widget.js`))
traefik.http.routers.wegaria-feedback.priority: "100"
traefik.http.routers.wegaria-feedback.entrypoints: websecure
traefik.http.routers.wegaria-feedback.tls: "true"
traefik.http.routers.wegaria-feedback.middlewares: wegaria-feedback-strip
traefik.http.routers.wegaria-feedback.service: feedback@docker
traefik.http.middlewares.wegaria-feedback-strip.stripprefix.prefixes: /_feedback
  • Only these two paths, never /_feedback/api, /_feedback/auth or /_feedback/admin. Otherwise the administration and API of the feedback service would be reachable under Wegaria's host.
  • Both paths run without Authelia, on purpose: the widget also runs on the public status page. The feedback service checks key and allowed origin itself.
  • In the feedback service, enter https://${WEGARIA_HOST} as an allowed origin for the project and set TRUST_PROXY=1 there.
  • Without these labels, /_feedback/widget.js answers 404: the widget does not appear and Wegaria works unchanged.
  • To try it locally, see Feedback (demo/traefik.yml).

Alternative: native OIDC instead of forward auth

Then the headers, trustedProxies and the Authelia middleware are no longer needed, and Wegaria is reachable without forward auth:

baseUrl: https://wegaria.example.com
auth:
  mode: oidc
  issuer: https://auth.example.com
  clientId: wegaria
  clientSecret: ${env:OIDC_CLIENT_SECRET}

In the Compose file, only remove middlewares (the line with wegaria-strip-identity,authelia@docker). Redirect URI at the IdP: https://wegaria.example.com/auth/callback. Details: Authentication.

Applications from Docker labels (optional)

docker: in wegaria.yaml lets Wegaria read tiles from container labels (structure and labels: Applications). To use it, enable the commented-out service dockerproxy in deploy/compose.yaml and set endpoint: http://dockerproxy:2375.

  • Wegaria never gets the Docker socket, only the proxy. The proxy runs in its own internal network and allows only CONTAINERS=1.
  • The proxy still sees all containers and their labels (environment variables are not part of the container list; endpoints that would deliver them are blocked by the proxy).
  • defaultAccess: none is the safe start: new containers appear only once they carry wegaria.groups or wegaria.public.
  • The proxy is queried once at start-up; if it is unreachable, Wegaria starts anyway and fetches the list later.

Operations

  • Backup: the volume wegaria-data (SQLite in WAL mode; safest with the container stopped or with sqlite3 .backup). It also contains session.key, the key for stored tokens (native OIDC only). Keep database and key separately; then a leaked database backup is not enough to misuse tokens.
  • Updating: docker compose up -d --build. Database migrations run automatically at start-up.
  • Logs: docker compose logs -f wegaria. Failed configuration or content is shown there and, for adminGroups, at the top of the page.
  • Multiple instances: not supported (rate limits are kept in memory; queue and database are local). One instance is enough for an internal portal; users stay signed in across updates because sessions live in /data.
  • Notice editor (incidents.editable): the directory with the notices must be writable for the container; the rest of /config stays read-only:
    volumes:
  - ./config:/config:ro
  - ./status:/config/status      # writable; owner UID 1000 (user "node")
  • Time zone: set timezone: Europe/Berlin in wegaria.yaml; otherwise the container shows times in UTC.
  • Git action: mount the target directory as a volume and list it in targets. The container writes as the user node (UID 1000), so the directory must be writable for that UID. push needs credentials in the container (for example a deploy key); this is deliberately not preconfigured.
  • Private CA for internal backends or SMTP: set NODE_EXTRA_CA_CERTS=/config/ca.pem.
