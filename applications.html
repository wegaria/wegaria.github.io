Applications

Applications are shown as tiles on the start page, grouped into sections. Tiles are defined in wegaria.yaml and, optionally, discovered from Docker container labels.

Tiles and sections

sections:
  - title: Daily work
    access: { groups: [staff] }          # optional, applies to all tiles of the section
    items:
      - title: Mail
        id: mail                         # optional; default: slug of the title
        url: https://mail.example.com
        description: Webmail
        icon: "lucide:mail"
        newTab: true                     # default true
        docs:
          - { title: Manual, url: https://wiki.example.com/mail }
        searchOnly: false
        access: { groups: [staff], deny: [guests] }
        status: { provider: kuma, monitor: Mail }
Tile field Meaning
title Name of the tile (required).
id Lower-case letters, digits and dashes. Referenced by affects in incidents and by apps in service pages and home.defaults. Default: a slug of the title. Duplicate ids are rejected.
url An http(s), mailto: or tel: URL or an absolute path (no javascript:).
description Optional text; also searched.
icon See icons.
newTab Open in a new tab (default true).
docs List of { title, url } links to documentation outside Wegaria (http(s) only). See application pages.
searchOnly Not shown on the start page, not hideable, but found by the search. For rarely needed applications.
access { groups, deny, public }, see Access rules.
status Status dot from a provider, see Status.

Tile ids used in home.defaults must exist; unknown ids are rejected by the configuration check.

Application pages and documentation

If an application has something stored for it, its tile shows a book symbol (otherwise not) and leads to /app/<tile-id>.

At the top are the name, the state and, like the strip on the start page, the current notices and maintenance of this application (without the navigation row and search of the other pages). Below, on the left, the documentation is listed by headings (together with further links and related requests); on the right the selected page appears in full (?doc=<page-id>; without a selection, the first one).

Documentation can be attached in two ways:

  • External: docs: [{ title: Manual, url: https://wiki.example.com/mail }] on the tile (Docker: label wegaria.docs.<title>: <url>).
  • Inside Wegaria: FAQ pages and forms of the service area name the tile in their header with apps: [mail] (Markdown front matter or form YAML). This also allows several runbooks per application, maintained as Markdown.

Details for pages kept inside Wegaria:

  • Every page has its own permissions: those of its category (for example a category "Operations" for it only) and, optionally, access: in the header of the file. Someone who may not see a page gets it neither in the list nor through ?doc= (and the tile may show no book symbol for that person).
  • The heading in the list is by default the title of the category. Override it with group: Operations in the header of the file. order determines the sequence.
  • Do not put credentials into these pages: they are visible to everyone who may see the page.
  • Unknown tile ids in apps are reported to adminGroups as a hint.

Search

One search covers everything the user may see:

  • applications (title, description, section),
  • the service area (FAQ, forms),
  • news (what the feeds deliver, not an archive).

On the start page the field shows a menu above the page while typing (/search/live, from 2 characters; arrow keys; Esc or a click outside closes it). Applications appear in it like the tiles, with icon and status. Without JavaScript, and on all other pages, the field leads to the results page /search. Permissions are applied before a hit is returned.

On the news page the search field filters the news instead; see News.

Applications from Docker labels

Instead of maintaining every tile in wegaria.yaml, Wegaria can read applications from the labels of running containers. A read-only Docker socket proxy is enough (for example tecnativa/docker-socket-proxy with CONTAINERS=1, everything else off). Wegaria never gets the Docker socket itself.

docker:
  endpoint: http://dockerproxy:2375
  defaultAccess: none          # all | none: containers without a permission label are seen by all signed-in users / by nobody
  defaultGroup: Other applications   # section used when no group label is set
  intervalSeconds: 30
Field Default Meaning
endpoint required http(s) URL of the Docker socket proxy. Needs CONTAINERS=1 only.
auth none Optional credentials for the proxy (same format as for providers).
defaultAccess required all or none for containers without wegaria.groups, wegaria.deny or wegaria.public.
defaultGroup Weitere Anwendungen Section for containers without a group label.
intervalSeconds 30 Polling interval (minimum 5).

The labels of Homepage are read (homepage.group, .name, .href, .description, .icon, .weight), so existing containers appear without changes. Wegaria's own wegaria.* labels take precedence and add what Homepage does not know, above all the permissions:

Label Meaning
wegaria.enable true/false. Without the label, every container with wegaria.title or homepage.name counts.
wegaria.title, wegaria.url, wegaria.description, wegaria.icon, wegaria.group, wegaria.weight, wegaria.id, wegaria.newTab, wegaria.searchOnly Like the fields of a tile.
wegaria.docs.<title> Documentation link (value: URL), like docs on a tile.
wegaria.groups, wegaria.deny Comma-separated groups that may or may not see the application.
wegaria.public true = visible even without signing in (status page).
wegaria.status.provider + .monitor / .endpoint / .query Status dot, like status: on a tile.
wegaria.status.public true = only the state is shown on /status to everyone, even if the tile itself is not visible.

Notes:

  • Homepage icons such as sh-nextcloud (dashboard-icons CDN) are not loaded; the initials appear until wegaria.icon is set. With icons.dir, homepage.icon: grafana is mapped to the local logo; see Icons.
  • Configured tiles always take precedence. If a section has the same title in both places, the two are merged.
  • Faulty containers are skipped with a warning in the log.
  • If the proxy fails, the last list stays in place.
  • Changes to docker: need a restart.
  • Wegaria queries the proxy once at start-up; if it is unreachable, Wegaria starts anyway and fetches the list later.
  • defaultAccess: none is the safe start: new containers appear only once they carry wegaria.groups or wegaria.public.

For the proxy setup in Compose (own internal network, what the proxy can still see), see Deployment.
